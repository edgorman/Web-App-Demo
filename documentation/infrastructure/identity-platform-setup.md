# Google Identity Platform Setup Guide

This guide explains how to set up Google Identity Platform for a new environment using our automated bootstrap scripts.

## Overview

The setup process has been fully automated to eliminate manual steps. You no longer need to:
- ❌ Manually create OAuth credentials in GCP Console
- ❌ Manually copy and paste client IDs and secrets
- ❌ Manually retrieve Identity Platform API keys
- ❌ Manually populate Secret Manager

Instead, run two simple scripts that handle everything automatically.

## Prerequisites

Before you begin, ensure you have:

1. **GCP Project Created**: Your environment project (e.g., `web-app-demo-dev`)
2. **gcloud CLI**: Installed and authenticated (`gcloud auth login`)
3. **jq**: JSON processor installed (`sudo apt-get install jq` or `brew install jq`)
4. **Permissions**: Project Owner or the following roles:
   - Identity Platform Admin
   - Secret Manager Admin
   - Service Usage Admin
   - OAuth Config Editor

5. **Repository Cloned**: This repository on your local machine

## Step-by-Step Setup

### Step 1: Run Bootstrap Script

This script creates OAuth credentials and stores them in Secret Manager.

```bash
./infrastructure/scripts/bootstrap-identity-platform.sh <project-id> <environment>
```

**Example for dev environment**:
```bash
./infrastructure/scripts/bootstrap-identity-platform.sh web-app-demo-dev dev
```

**What happens**:
1. ✅ Enables required APIs (Identity Platform, Secret Manager, IAP)
2. ✅ Creates OAuth consent screen (if needed)
3. ✅ Creates OAuth client credentials
4. ✅ Stores credentials in Secret Manager
5. ✅ Generates `infrastructure/config/dev/terraform.tfvars`

**Output**:
```
✓ APIs enabled
✓ OAuth brand created
✓ OAuth client created
  Client ID: 123456789-abc123.apps.googleusercontent.com
✓ OAuth credentials stored in Secret Manager
✓ Created infrastructure/config/dev/terraform.tfvars

Next steps:
  1. Review terraform.tfvars
  2. Run Terraform
  3. Run post-terraform script
```

### Step 2: Apply Terraform Configuration

Navigate to the infrastructure environment directory and apply:

```bash
cd infrastructure/env
terraform init
terraform apply -var-file=../config/dev/terraform.tfvars
```

**What this creates**:
- Identity Platform configuration
- Google OAuth provider configuration
- Authorized domains (localhost + Cloud Run URLs)
- Secret Manager resources
- Cloud Run services (frontend + backend)

**Review the plan** before applying to ensure everything looks correct.

### Step 3: Run Post-Terraform Script

This script retrieves the auto-created Identity Platform API key.

```bash
cd ../..
./infrastructure/scripts/post-terraform-identity-platform.sh web-app-demo-dev dev
```

**What happens**:
1. ✅ Retrieves Identity Platform API key
2. ✅ Stores API key in Secret Manager

**Output**:
```
✓ API key retrieved
✓ API key stored in Secret Manager

Post-Terraform Setup Complete!
```

### Step 4: Verify Setup

Verify that all secrets are properly stored:

```bash
# List secrets
gcloud secrets list --project=web-app-demo-dev

# Verify each secret (shows metadata, not actual value)
gcloud secrets describe google_oauth_client_id --project=web-app-demo-dev
gcloud secrets describe google_oauth_client_secret --project=web-app-demo-dev
gcloud secrets describe identity_platform_api_key --project=web-app-demo-dev
```

Expected output: All three secrets exist with status "ENABLED".

## What Gets Created

### In GCP Console

**Identity Platform**:
- Sign-in configuration
- Google as OAuth provider
- Authorized domains: localhost, backend URL, frontend URL

**Secrets in Secret Manager**:
| Secret Name | Description | Used By |
|------------|-------------|---------|
| `google_oauth_client_id` | OAuth 2.0 Client ID | Terraform, Frontend |
| `google_oauth_client_secret` | OAuth 2.0 Client Secret | Terraform |
| `identity_platform_api_key` | Web API Key | Frontend |

**OAuth Consent Screen**:
- Application title: "Web App Demo - {environment}"
- Support email: Your gcloud account email

**OAuth Client**:
- Display name: `identity-platform-{environment}`
- Type: Web application
- Authorized domains: Configured in Identity Platform

### In Your Repository

**File: `infrastructure/config/{environment}/terraform.tfvars`**:
```hcl
# Auto-generated by bootstrap-identity-platform.sh
project_id = "web-app-demo-dev"
google_oauth_client_id = "123456789-abc123.apps.googleusercontent.com"
google_oauth_client_secret = "GOCSPX-xxxxxxxxxxxx"
```

⚠️ **Important**: This file contains secrets and should NOT be committed to version control. It's already in `.gitignore`.

## CI/CD Integration

GitHub Actions workflows automatically inject secrets from Secret Manager:

```yaml
- name: Inject OAuth Credentials
  run: |
    CLIENT_ID=$(gcloud secrets versions access latest \
      --secret="google_oauth_client_id" \
      --project="${{ inputs.project_id }}")
    CLIENT_SECRET=$(gcloud secrets versions access latest \
      --secret="google_oauth_client_secret" \
      --project="${{ inputs.project_id }}")
    
    echo "TF_VAR_google_oauth_client_id=$CLIENT_ID" >> $GITHUB_ENV
    echo "TF_VAR_google_oauth_client_secret=$CLIENT_SECRET" >> $GITHUB_ENV
```

This means:
- ✅ No secrets in GitHub repository
- ✅ No secrets in GitHub Secrets
- ✅ All secrets centralized in GCP Secret Manager
- ✅ Automatic injection during deployment

## Common Scenarios

### Setting Up Multiple Environments

Run the bootstrap process for each environment:

```bash
# Dev
./infrastructure/scripts/bootstrap-identity-platform.sh web-app-demo-dev dev

# Staging
./infrastructure/scripts/bootstrap-identity-platform.sh web-app-demo-staging staging

# Production
./infrastructure/scripts/bootstrap-identity-platform.sh web-app-demo-prod prod
```

Each environment gets:
- Separate OAuth client
- Separate secrets in its own Secret Manager
- Separate Terraform state

### Rotating OAuth Credentials

To rotate credentials (recommended periodically):

```bash
# Re-run bootstrap script
./infrastructure/scripts/bootstrap-identity-platform.sh web-app-demo-dev dev

# Script will prompt: create new client or use existing
# Choose "create new" by pressing Enter

# Update Terraform state
cd infrastructure/env
terraform apply -var-file=../config/dev/terraform.tfvars

# Redeploy services to pick up new credentials
```

### Recovering from Lost Secrets

If you lose the OAuth client secret:

1. Re-run bootstrap script:
   ```bash
   ./infrastructure/scripts/bootstrap-identity-platform.sh web-app-demo-dev dev
   ```

2. When prompted about existing client, press Enter to create a new one

3. Update Terraform:
   ```bash
   cd infrastructure/env
   terraform apply -var-file=../config/dev/terraform.tfvars
   ```

4. (Optional) Delete old OAuth client from GCP Console

## Troubleshooting

### "Service account does not have permission"

**Problem**: gcloud user lacks required permissions

**Solution**:
```bash
# Grant yourself necessary roles
PROJECT_ID="web-app-demo-dev"
USER_EMAIL="your-email@example.com"

gcloud projects add-iam-policy-binding $PROJECT_ID \
  --member="user:$USER_EMAIL" \
  --role="roles/editor"

gcloud projects add-iam-policy-binding $PROJECT_ID \
  --member="user:$USER_EMAIL" \
  --role="roles/secretmanager.admin"
```

### "OAuth brand already exists"

**Problem**: This is actually normal!

**Solution**: The script will use the existing brand. No action needed.

### "Cannot find API key"

**Problem**: API key not created yet or different name

**Solution**:
1. Go to GCP Console → APIs & Credentials
2. Find the Browser key (auto-created by Identity Platform)
3. Copy the key value
4. Paste when script prompts you

### "jq: command not found"

**Problem**: JSON processor not installed

**Solution**:
```bash
# Ubuntu/Debian
sudo apt-get install jq

# macOS
brew install jq

# Or install from https://stedolan.github.io/jq/download/
```

## Security Considerations

### Secret Storage

- ✅ All secrets stored in Google Secret Manager
- ✅ Secrets encrypted at rest and in transit
- ✅ Access logged via Cloud Audit Logs
- ✅ IAM controls who can access secrets

### OAuth Client Security

- Use separate OAuth clients per environment
- Regularly rotate credentials (every 90 days recommended)
- Monitor OAuth usage in GCP Console
- Set up alerts for unusual authentication patterns

### Terraform State

- Terraform state may contain sensitive data
- Use remote state backend (GCS) with encryption
- Restrict access to state files
- Never commit state files to version control

### Best Practices

1. **Principle of Least Privilege**: Grant minimal permissions
2. **Audit Access**: Review Secret Manager access logs regularly
3. **Rotate Regularly**: Update OAuth credentials every 90 days
4. **Monitor Usage**: Set up alerts for API quota and errors
5. **Backup Secrets**: Document recovery procedures
